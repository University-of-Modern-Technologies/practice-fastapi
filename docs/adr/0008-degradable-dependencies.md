# 0008. Кеш і журнал подій — залежності, без яких API працює далі

**Статус:** прийнято

## Контекст

API залежить від трьох сховищ. Без PostgreSQL воно не має сенсу: там усі дані.
Redis і MongoDB інші. Redis тримає кеш (набори дозволів, звіти, відповіді
AI-помічника) і лічильники обмеження частоти запитів. MongoDB тримає журнал
подій ([0001](0001-two-stores.md)). Жодне з них не потрібне, щоб правильно
виконати бізнес-операцію.

Якщо кожна помилка Redis чи MongoDB перетворюється на `500`, недоступність
допоміжного сховища кладе всю систему, хоча дані в повному порядку.

## Рішення

- **Кеш відкритий при збої** (`backend/app/cache/service.py`). Помилка
  читання означає «у кеші нічого немає», і значення береться з джерела.
  Помилка запису лише логується. Пошкоджений запис видаляється.
- **Обмеження частоти** при недоступному Redis пропускає запити
  (`backend/app/middleware/rate_limit.py`).
- **Журнал подій** дописується «вистрілив і забув»: `append` ніколи не кидає
  (`backend/app/events/service.py`), а доставка подій відокремлена від запиту
  ([0002](0002-domain-events-after-commit.md)). API стартує й тоді, коли MongoDB
  недоступна: `connect` лише записує помилку в лог, а драйвер перепідключається
  сам, і дописування відновлюються без перезапуску
  (`backend/app/events/connection.py`).
- **Перевірка готовності** `/api/health/ready` називає кожну залежність
  поіменно, але оцінює їх по-різному (`backend/app/health/readiness.py`,
  `backend/app/health/routes.py`):
  - база недоступна — `503 not_ready`;
  - кеш недоступний — `200 degraded`: перевірку кешу позначено некритичною
    (`critical=False` у `backend/app/cache/client.py`), бо його відсутність
    коштує швидкості, а не правильності;
  - журнал недоступний — `503 not_ready`: запити обслуговуються, але
    екземпляр, який мовчки втрачає історію, виводиться з ротації.
- `INFRA_PROFILE=offline` (`backend/app/infra_profile.py`) вмикає кеш без
  зовнішнього сховища разом із заглушками AI-помічника й доставки
  ([0009](0009-integrations-behind-interfaces.md)).

## Наслідки

- Падіння Redis робить систему повільнішою, але не зламаною. Падіння MongoDB
  зупиняє лише запис історії.
- «API працює» і «API готовий» — різні твердження. Без MongoDB запит до API
  проходить, але `/api/health/ready` відповідає `503`. Контейнер `api` у
  `compose.yaml` перевіряє саме готовність, тож у Docker такий екземпляр
  вважається нездоровим, а nginx без здорового `api` не стартує.
- Помилки допоміжних сховищ не видно користувачеві, і саме тому їх видно лише в
  логах і в `/api/health/ready`. Хтось має туди дивитися: у справжньому
  розгортанні це робота моніторингу.
- Без Redis обмеження частоти не діє, а без кешу кожен запит читає дозволи з
  бази. Під навантаженням це помітно.
- Новий код, що звертається до Redis чи MongoDB, мусить дотримуватися того
  самого правила: помилка допоміжного сховища — лог і обхідний шлях, а не
  виняток угору.
