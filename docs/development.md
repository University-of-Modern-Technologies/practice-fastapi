# Розробка

Як працювати з кодом щодня: запустити те, що правиш, прогнати тести, змінити
схему бази, наповнити її даними й оновити опис API. Перший запуск системи
описано в [README.md](../README.md), будову коду — в
[ARCHITECTURE.md](../ARCHITECTURE.md).

Усі команди `uv run poe …` виконуються з кореня репозиторію й однаково працюють
у PowerShell, cmd, bash і zsh. `uv run poe` без аргументів показує їх перелік з
описом. Команди `uv run alembic …`, `uv run pytest …` і `uv run python -m …`
виконуються з теки `backend`.

## Підготовка

```bash
uv run poe setup          # .env і backend/.env з новими секретами, перевірка портів, хук перед комітом
uv run poe local:install  # залежності бекенда (uv sync) і клієнта (npm ci)
```

`setup` не перезаписує наявні `.env`. Без нього достатньо скопіювати
`.env.example` у `.env` і `backend/.env.example` у `backend/.env`: шаблони
містять робочі локальні значення.

## Що запускати

Сховища завжди працюють у Docker. API й клієнт — у Docker або на машині.

| Що правиш | Команди | Де відкрити |
|---|---|---|
| бекенд | `uv run poe local:api` | http://localhost:8000/api/docs |
| бекенд і клієнт | `uv run poe local:api`, у другому терміналі `uv run poe local:web` | http://localhost:3000 |
| лише клієнт | `uv run poe docker:api`, потім `uv run poe local:web` | http://localhost:3000 |
| нічого, лише дивишся | `uv run poe docker:all` | http://localhost:8080 |
| перевірити production-збірку | `uv run poe docker:prod` | http://localhost:8080 |

- `local:api` спершу виконує `docker:db` (сховища, міграції, базове
  наповнення), потім запускає `python -m app.main` з перезапуском при
  збереженні. Логи кольорові; SQL-запити з параметрами видно в консолі, якщо
  в `backend/.env` стоїть `LOG_SQL=true`.
- `local:web` запускає `next dev` і пересилає `/api` на
  `http://127.0.0.1:<API_PORT>`. Йому байдуже, хто там слухає: контейнер `api`
  чи `local:api`.
- На порту API одночасно працює щось одне. `local:api` перевіряє порт
  заздалегідь і не стартує, якщо його тримає контейнер, — тоді спершу
  `uv run poe docker:stop`.
- Процеси на машині зупиняються `Ctrl+C`, усе докерне — `uv run poe docker:stop`.
- `uv run poe docker:logs api` — логи одного контейнера, `uv run poe docker:ps` —
  стан усіх.

## Перевірки бекенда окремо

З теки `backend`:

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy
uv run pytest
```

Саме ці чотири кроки й у цьому порядку виконує `uv run poe check:api`.

## Тести

| Набір | Де | Що потрібно | Команда |
|---|---|---|---|
| unit | `backend/tests/unit` | нічого | `uv run poe test` або `uv run pytest` у `backend` |
| contract | `backend/tests/contract` | нічого | входить у ті самі команди |
| integration | `backend/tests/integration` | запущені сховища | `uv run poe docker:db`, потім `uv run poe test:integration` |
| клієнт | `frontend/` | `uv run poe local:install` | входить у `uv run poe test` |

`uv run poe test` запускає юніт-тести бекенда, потім клієнта.

Окремий файл, клас чи тест — звичайними засобами pytest з теки `backend`:

```bash
uv run pytest tests/unit/test_products_service.py
uv run pytest -k version_conflict
uv run pytest --cov            # покриття коду теки app
```

**Інтеграційні тести.** Звичайний `pytest` їх не збирає (`-m "not integration"`
у `backend/pyproject.toml`) і в підсумку пише, скільки відкладено. Окремий
прогін — `uv run poe test:integration` або з теки `backend`:

```bash
uv run pytest -m integration
uv run pytest -m integration tests/integration/test_rbac_scope.py
```

Контейнерів тести не запускають і робочих даних не чіпають. Прогін бере хост,
порт, користувача й пароль з тих самих `.env` і сам виводить тестове оточення:

| Що | У тестах |
|---|---|
| `APP_ENV` | `test` |
| PostgreSQL | той самий сервер, база `${POSTGRES_DB}_test`; прогін створює її, накочує міграції й очищає таблиці |
| MongoDB | той самий сервер, база `${MONGO_DB}_test` |
| Redis | той самий сервер, ключі з префіксом `crm-test:` |

`DATABASE_URL_TEST`, `REDIS_URL_TEST` і `MONGODB_URL_TEST` перекривають
виведені адреси — так їх задає CI. Назва тестової бази мусить містити окреме
слово `test` або `testing`, інакше прогін відмовляється стартувати. Якщо
сховище не відповідає, прогін зупиняється до першого тесту з ненульовим кодом,
називає сховище й підказує `docker:db`.

## Перед комітом і перед pull request

| Команда | Що виконує |
|---|---|
| `uv run poe check` | `check:api`, потім `check:web` — усе, що перевіряє CI |
| `uv run poe check:api` | `ruff format --check`, `ruff check`, `mypy`, `pytest` у `backend` |
| `uv run poe check:web` | `npm run ci` у `frontend`: формат, лінт, типи, тести, збірка |

CI запускає ті самі команди, тож зелений `check` на машині означає зелені
перевірки в pull request. Інтеграційні тести, узгодженість міграцій із
моделями й збірка образів у CI йдуть окремими задачами.

**Хук перед комітом.** `setup` ставить git-хук (prek, конфігурація в
`.pre-commit-config.yaml`). Він форматує й лінтить лише файли, що йдуть у коміт:
ruff для `backend/`, eslint і prettier для `frontend/`. Тести хук не запускає.
Якщо хук щось виправив, коміт зупиняється: переглянь правки, зроби `git add` і
закоміть ще раз.

## Міграції

Схему бази описують моделі в `backend/app/db/models/`, а міграції Alembic у
`backend/migrations/versions/` переводять базу з однієї версії в іншу. Alembic
бере адресу бази з тих самих налаштувань, що й застосунок, тож потребує
заповнених `.env` і запущеного `docker:db`.

**Застосувати** — з кореня `uv run poe db:migrate` (у Docker, разом із базовим
наповненням) або з теки `backend`:

```bash
uv run alembic upgrade head
uv run alembic current            # на якій версії база
uv run alembic history            # ланцюжок міграцій
```

`docker:db`, `docker:api`, `docker:all` і `local:api` застосовують міграції самі.

**Створити** після зміни моделей:

```bash
uv run alembic revision --autogenerate --rev-id 0003_short_name -m "short name"
```

Ідентифікатори ревізій у цій базі — порядковий номер і коротка назва
(`0001_initial`); без `--rev-id` Alembic дасть випадковий шістнадцятковий.
Згенероване завжди треба прочитати: автогенерація бачить колонки й таблиці, але
не наміри — перейменування поля вона запише як видалення старого й додавання
нового. Кожна наявна міграція має `downgrade()`; нова теж повинна.

**Перевірити:**

```bash
uv run alembic check              # чи описують моделі те саме, що створюють міграції
uv run alembic upgrade head --sql # SQL без підключення до бази
uv run alembic downgrade -1       # відкотити останню міграцію
```

`alembic check` падає, якщо моделі й міграції розійшлися, і друкує операції,
які він би згенерував. CI робить те саме на порожній базі. Проба
`/api/health/ready` теж показує базу недоступною, якщо схему не накочено.

## Базове й демонстраційне наповнення

| Що | Команда | Що робить |
|---|---|---|
| базове | `uv run poe db:migrate` або `uv run python -m scripts.seed` у `backend` | ролі й дозволи, облікові записи з README, невеликий набір контактів, угод, товарів, складів і замовлень, налаштування організації; наповнює лише порожню базу — якщо користувачі вже є, нічого не змінює |
| демонстраційне | `uv run poe db:seed:demo` або `uv run python -m scripts.demo_seed` у `backend` | великий набір поверх базового: контакти, угоди, замовлення, рухи товару, аудит |

- Перезапуск стека не повертає змінені паролі й залишки: базове наповнення
  пропускає базу, де вже є користувачі. Повернутися до початкових даних —
  `uv run poe docker:clean`, потім `uv run poe docker:db`.
- Базове наповнення читає пароль облікових записів із `SEED_USER_PASSWORD`
  (щонайменше 12 символів, не `change-me`). У `APP_ENV=production` воно
  запускається лише з `SEED_ALLOW_PRODUCTION=true`.
- Демонстраційний набір потребує базового (ролі шукаються за назвою), бере
  рядки з `backend/scripts/demo_data/` і видаляє лише те, що сам записав минулого
  разу, тож запускати його можна скільки завгодно разів.
- `uv run poe db:seed:demo` працює в контейнері; `python -m scripts.demo_seed` —
  проти бази, до якої ведуть `.env`.
- Почати з порожньої бази: `uv run poe docker:clean`, потім `uv run poe docker:db`.

## Опис API

Опис OpenAPI генерується з маршрутів і Pydantic-моделей; як саме — у
[ARCHITECTURE.md](../ARCHITECTURE.md#опис-api-openapi). Закомічений
`backend/openapi.json` — це те, що код описує зараз, і він повинен змінюватися в
тому самому коміті, що й код.

Після будь-якої зміни маршруту, схеми запиту чи відповіді або оголошених
відмов — з теки `backend`:

```bash
uv run python -m scripts.export_openapi
```

Скрипт не читає ні змінних оточення, ні `.env` і не підключається до сховищ,
тож на кожній машині пише той самий файл. Якщо забути, впаде
`tests/unit/test_openapi_document.py` (у `pytest`, `check:api` і CI) з
підказкою цієї ж команди. Той самий тест падає, якщо маршрут змонтовано, але він
не потрапив в опис.

Новий маршрут, що може відмовити, оголошує відмови поруч зі шляхом:

```python
@router.patch("/{id}", summary="Оновити товар", responses=refusals(401, 403, 404, 409))
```

400 і 500 додаються до кожної операції самі. Переглянути результат —
http://localhost:8000/api/docs.

## Змінні оточення бекенда

API читає значення в такому порядку, перше знайдене перемагає:

1. змінні процесу (у Docker — блок `environment` у `compose.yaml` і
   `compose.override.yaml`);
2. `backend/.env`;
3. `.env` у корені.

Обидва файли шукаються від теки бекенда, хоч би звідки запущено застосунок,
міграції, наповнення чи тести. Кожна змінна, що має значення за замовчуванням у
коді, може бути відсутня; порожнє значення (`KEY=`) означає те саме, що
відсутнє. Перевіряє все `backend/app/core/settings.py`; невалідне значення
зупиняє старт із переліком помилок.

### Спільні, з кореневого `.env`

| Змінна | Що означає | Типово |
|---|---|---|
| `APP_ENV` | `development`, `test` або `production`; що від нього залежить — у [ARCHITECTURE.md](../ARCHITECTURE.md#середовища). У Docker задається compose-файлами | `development` |
| `API_PORT` | порт API назовні; API на машині слухає його, якщо не задано `PORT` | — |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | база й облікові дані PostgreSQL | — |
| `POSTGRES_HOST`, `POSTGRES_PORT` | де PostgreSQL | `127.0.0.1`, `5432` |
| `REDIS_HOST`, `REDIS_PORT` | де Redis | `127.0.0.1`, `6379` |
| `MONGO_DB`, `MONGO_USER`, `MONGO_PASSWORD` | база журналу подій і облікові дані MongoDB | — |
| `MONGO_HOST`, `MONGO_PORT` | де MongoDB | `127.0.0.1`, `27017` |

У шаблонах `.env` хости лише закоментовані: на машині підходить типовий `127.0.0.1`, а в
Docker `compose.yaml` ставить імена сервісів. Саме `127.0.0.1`, а не `localhost`: на
Windows `localhost` спершу пробує IPv6, і кожне з'єднання зі сховищем чекає на
це дві секунди.

`PROJECT_NAME`, `HTTP_PORT`, `WEB_PORT`, `PORTAINER_PORT` читає лише Docker
Compose; таблиця портів — у README.

### Адреси сховищ

| Змінна | Що означає | Типово |
|---|---|---|
| `DATABASE_URL` | адреса PostgreSQL; драйвер `asyncpg` додається сам | збирається з `POSTGRES_*` |
| `REDIS_URL` | адреса Redis | збирається з `REDIS_*` |
| `MONGODB_URL` | адреса MongoDB | збирається з `MONGO_*` |

Явна адреса перемагає зібрану. Писати її варто лише тоді, коли API треба
направити на інший сервер; забута стара адреса в `backend/.env` — найчастіша
причина «пароль не підходить».

### `backend/.env`

**Сервер**

| Змінна | Що означає | Типово |
|---|---|---|
| `HOST` | адреса, яку слухає API на машині | `0.0.0.0` |
| `PORT` | порт API на машині; перемагає `API_PORT`. У Docker завжди `8000` | `8000` |
| `LOG_LEVEL` | `critical`, `error`, `warning`, `info`, `debug`; приймаються й `fatal`, `warn`, `trace`, `silent` | `info` |
| `CORS_ORIGINS` | дозволені джерела браузера, через кому або JSON-масивом; `*` — будь-яке. У Docker `compose.yaml` ставить адресу nginx | `http://localhost:3000` |
| `JSON_BODY_LIMIT_BYTES` | найбільше тіло запиту, від 1024 до 67108864; більше тіло, зокрема передане частинами (chunked), дістає 413 | `1048576` |
| `TRUSTED_PROXIES` | адреси чи CIDR-мережі проксі через кому, яким API вірить щодо адреси клієнта (`X-Forwarded-For`); `*` не приймається. У Docker `compose.yaml` ставить `172.16.0.0/12` — мережу, з якої приходить nginx | — (адреса клієнта є адресою з'єднання) |
| `LOG_SQL` | `true` — журнал кожного SQL-запиту з параметрами; у production не діє | `false` |
| `API_DOCS_ENABLED` | `true` / `false` — Swagger UI і `/api/openapi.json`; порожнє значення вмикає їх скрізь, крім `production` | порожньо |
| `METRICS_TOKEN` | токен для `/api/metrics`, щонайменше 16 символів; без нього ендпоінта метрик немає | — |
| `SHUTDOWN_GRACE_PERIOD_MS` | скільки після сигналу зупинки проба готовності відповідає 503, перш ніж закриваються з'єднання | `10000` |
| `SHUTDOWN_TIMEOUT_MS` | скільки сервер чекає завершення запитів під час зупинки; округлюється вгору до цілих секунд, щонайменше 1 | `15000` |

**Автентифікація й наповнення**

| Змінна | Що означає | Типово |
|---|---|---|
| `JWT_ACCESS_SECRET` | секрет підпису access-токена, щонайменше 32 символи | обов'язкова |
| `JWT_REFRESH_SECRET` | обов'язкова, щонайменше 32 символи; refresh-токен не є JWT (див. ARCHITECTURE.md), тож у підписі цей секрет не бере участі | обов'язкова |
| `SEED_USER_PASSWORD` | пароль облікових записів базового й демонстраційного наповнення; від 12 символів, не `change-me`. Читає лише `scripts/seed.py` | — |
| `SEED_ALLOW_PRODUCTION` | дозволяє базове наповнення при `APP_ENV=production` | `false` |

`setup` генерує обидва JWT-секрети заново для кожного клону.

**Кеш, ліміти, події**

| Змінна | Що означає | Типово |
|---|---|---|

| `CACHE_TTL_SECONDS` | скільки живуть звіти, дозволи й налаштування в кеші | `300` |

| `AI_MAX_ATTEMPTS` | спроб на одну відповідь | `2` |
| `AI_MAX_TOKENS` | найбільша довжина відповіді моделі | `400` |
| `AI_MAX_INPUT_CHARS` | найбільший обсяг тексту, що йде в модель | `4000` |
| `AI_CACHE_TTL_SECONDS` | скільки відповідь живе в кеші | `300` |

**Телефонія.** Порожній `CALL_PROVIDER_BASE_URL` залишає вбудовану заглушку.

| Змінна | Що означає | Типово |
|---|---|---|
| `CALL_PROVIDER_BASE_URL` | адреса API телефонії | — |
| `CALL_PROVIDER_API_KEY` | ключ до нього | — |
| `CALL_PROVIDER_TIMEOUT_MS` | тайм-аут одного звернення | `5000` |
| `CALL_PROVIDER_MAX_ATTEMPTS` | спроб на одне звернення | `3` |
| `CALL_PROVIDER_BACKOFF_MS` | пауза між спробами | `200` |
| `CALL_SYNC_BATCH_SIZE` | скільки дзвінків бере одна синхронізація | `100` |

**Профіль залежностей**

| Змінна | Що означає | Типово |
|---|---|---|
| `INFRA_PROFILE` | `offline` — усі заміни разом: AI-макет, заглушки доставки й телефонії, кеш без Redis; `live` — кожна залежність обирає сама за своїми змінними | `live` |

Ліміт запитів і журнал подій від профілю не залежать: вони й далі звертаються до
Redis і MongoDB.

### Для інтеграційних тестів

| Змінна | Що означає | Типово |
|---|---|---|
| `DATABASE_URL_TEST` | адреса тестової бази PostgreSQL | `${POSTGRES_DB}_test` на тому самому сервері |
| `REDIS_URL_TEST` | адреса тестового Redis | той самий сервер |
| `MONGODB_URL_TEST` | адреса тестової бази MongoDB | `${MONGO_DB}_test` на тому самому сервері |

### Веб-клієнт

Власного `.env` клієнт не має: адреса API в ньому відносна, `/api/v1`. Ці
змінні фіксуються під час збірки образу, а для `next dev` — під час його старту:

| Змінна | Що означає | Типово |
|---|---|---|
| `API_ORIGIN` | куди `next dev` і контейнер `web` пересилають `/api` | `http://127.0.0.1:8000`; в образі `http://api:8000` |
| `NEXT_PUBLIC_API_URL` | інша базова адреса API | `/api/v1` |
| `NEXT_PUBLIC_WS_URL` | інша адреса каналу подій; порожнє значення вимикає канал | `ws://` або `wss://` на тому самому джерелі, шлях `/api/v1/realtime` |
