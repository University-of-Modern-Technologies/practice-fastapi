# CRM — веб-клієнт

Інтерфейс поверх API `/api/v1`. Клієнт не знає, яка реалізація стоїть за
контрактом, тому працює з будь-якою з backend-баз без змін у коді.

## Запуск

Разом з усім стеком — з теки backend-бази:

```bash
docker compose up -d --build
```

Клієнт стане доступним на <http://localhost:3100>, API — на
<http://localhost:3000>.

Окремо, у режимі розробки:

```bash
cp .env.example .env.local   # вкажіть адресу API
npm ci
npm run dev
```

## Змінні середовища

| Змінна                | Призначення                                             |
| --------------------- | ------------------------------------------------------- |
| `NEXT_PUBLIC_API_URL` | базова адреса API, напр. `http://localhost:3000/api/v1` |
| `NEXT_PUBLIC_WS_URL`  | адреса каналу подій; порожнє значення вимикає його      |

Обидві потрапляють у бандл під час збірки, тому в Docker вони передаються
аргументами `--build-arg`, а не змінними контейнера.

## Як влаштований код

```text
src/
  app/            маршрути: (auth) — під сесією, (non-auth) — публічні
  components/     спільні компоненти інтерфейсу
  shared/
    api/          HTTP-клієнт, ApiError, типи відповідей
    auth/         вхід, вихід, стан сесії
    hooks/ stores/ constants/
  templates/      shell, провайдери, тема, навігація
```

Модуль тримає свій код поруч зі своєю сторінкою: `page.tsx`, `*.service.ts` —
чистий HTTP без React, `*.queries.ts` — хуки кешу, `_components/`, `_hooks/`.
Компонент ніколи не звертається до `fetch` напряму.

## Структура розділу

Кожен розділ — це тека в `src/app/(auth)/` з тим самим набором файлів:

```text
orders/
  page.tsx            маршрут: збирає дані з queries і розкладає їх по компонентах
  loading.tsx         скелетон, поки маршрут вантажиться
  orders.service.ts   HTTP: URL, тіла запитів, розпаковування відповіді
  orders.queries.ts   TanStack Query: ключі кешу, інвалідація, мутації
  orders.types.ts     типи контракту цього розділу
  orders.validation.ts   схеми Zod для форм
  _components/        компоненти лише цього розділу
  _hooks/             стан лише цього розділу (фільтри, чернетки форм)
```

Напрямок викликів завжди один: **`page.tsx` → `*.queries.ts` → `*.service.ts` →
HTTP-клієнт**. Стрибати через шар не можна — сторінка не звертається до сервісу
напряму, сервіс не знає про кеш.

Сервіс **не імпортує React**. Це не стильова вимога: сервіс — це чиста функція
від аргументів до відповіді, тому його можна прочитати як опис контракту й
покрити тестом без рендера. Щойно в ньому зʼявиться хук, він перестане бути
викликуваним поза компонентом, і тест доведеться писати через DOM.

Те, що потрібне більш ніж одному розділу, переїжджає в `src/components`,
`src/shared` або `src/lib` — у теці розділу лишається тільки те, що більше ніде
не використовується.

## Наскрізні правила

Порушення будь-якого з них — дефект, а не стильова розбіжність.

- **Гроші** — тільки через `Money` і `<MoneyValue/>`. Сума приходить рядком
  фіксованого масштабу (`"1234.50"`) і рядком лишається: жодного `Number` над
  грошима, бо `0.1 + 0.2` у платіжці помітно.
- **Дати** — тільки через `DateTime`. Форма працює з `dayjs`, на дріт іде
  ISO-рядок, у таблиці — `<DateValue/>`.
- **`version` і `409`** — картка тримає прочитаний `version` і надсилає його
  назад. Якщо запис змінили паралельно, сервер відповість `409`; його ловить
  `useVersionConflict` і пропонує перечитати запис, а не показує загальну
  помилку.
- **Переходи станів** — тільки `POST …/transitions`. У `PATCH` полів `stage` та
  `status` не існує, і клієнт їх не надсилає.
- **Дозволи** — кнопка дії загорнута в `PermissionGate` з тим самим
  `resource:action`, який вимагає сервер. Приховування — ввічливість до
  користувача; справжня перевірка лишається на API.

## Розділи, яких немає в частині збірок API

`analytics`, `integrations` і `ai` реалізовані не в кожній збірці API, а клієнт
не має способу дізнатися заздалегідь, з якою саме говорить. Тому їх відсутність
— очікувана відповідь, а не збій:

- перший запит розділу повертає `404` або взагалі не доходить, і сторінка
  показує «Розділ недоступний у поточній збірці API» (спільний компонент
  `ModuleUnavailable`) замість повідомлення про помилку;
- повторних спроб немає — запит, який щойно не знайшов маршруту, не знайде його
  й за секунду;
- пункт меню лишається на місці: сховати його клієнт не може, бо не знає, чи
  розділ відсутній, чи просто недоступний саме зараз;
- решта застосунку працює як звичайно.

Ознака «розділу немає» в кожному з трьох розділів своя. Наприклад, в
інтеграціях `404` неоднозначний: це або відсутній маршрут, або відправлення з
таким номером не знайдено — і плутати їх не можна.

## Канал подій

`NEXT_PUBLIC_WS_URL` вмикає канал подій: сервер повідомляє про зміни, а клієнт у
відповідь інвалідує відповідні ключі кешу. Порожнє значення — підтримуваний
режим: канал просто не вмикається, і застосунок працює на звичайних запитах.

Авторизація йде **підпротоколом** (`bearer` + токен), а не параметром URL —
адреси зʼєднань потрапляють у логи проксі, і токен там не потрібен. Токен живе
15 хвилин, тому клієнт перечитує його на кожне зʼєднання й перепідключається
після поновлення сесії.

## Сесія

Access-токен зберігається лише в пам'яті, refresh-токен — у httpOnly-cookie,
яку видає API. Перезавантаження сторінки відновлює сесію одним запитом
`POST /auth/refresh`. Якщо кілька запитів одночасно отримають `401`, поновлення
виконується один раз, після чого кожен запит повторюється рівно раз.

Помилка будь-якого запиту — це виняток `ApiError` з полями `status`, `code`,
`details` і `requestId`; невдалий виклик неможливо випадково прийняти за
успішний.
