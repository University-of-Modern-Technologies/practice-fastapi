# Навчальна CRM — запуск

Система складається з веб-клієнта (`frontend/`), HTTP API на Python (`backend/`)
і трьох сховищ: PostgreSQL, Redis і MongoDB. Усе разом піднімається однією
командою через Docker Compose.

## Вимоги

- Docker Desktop (або Docker Engine) з Docker Compose v2.
- [uv](https://docs.astral.sh/uv/) — для команд `uv run poe …` і для API на машині.
  Python 3.13 uv поставить сам.
- Node.js 22 — лише для веб-клієнта на машині (`dev:web`).

Без uv стек теж запускається, через bash-скрипти або напряму через Docker
Compose — див. «Без обгорток» нижче.

## Швидкий старт

```bash
uv run poe setup   # створює .env із новими секретами й перевіряє порти
uv run poe start   # збирає й піднімає стек, чекає, поки все стане здоровим
```

Відкрий **http://localhost:8080**. Перший запуск займає кілька хвилин через
збірку образів, наступні — секунди. Команди працюють у PowerShell, cmd, bash і
zsh. `uv run poe` без аргументів показує список команд з описом.

## Команди

| Команда | Що робить |
|---|---|
| `uv run poe setup` | створює `.env`, `backend/.env` і `frontend/.env.local`; секрети генерує нові; показує зайняті порти |
| `uv run poe start` | увесь стек у Docker у режимі розробки; API перезапускається при збереженні файла |
| `uv run poe stop` | зупинити стек; дані лишаються |
| `uv run poe build` | зібрати production-образи |
| `uv run poe prod:start` | стек із production-образів — так, як він працював би на сервері |
| `uv run poe prod:stop` | зупинити production-стек; дані лишаються |
| `uv run poe test` | тести бекенда й веб-клієнта, на машині |
| `uv run poe start:api` | лише API і його сховища, без клієнта й проксі |
| `uv run poe start:infra` | лише PostgreSQL, Redis і MongoDB — для API, запущеного на машині |
| `uv run poe dev` | API на машині, проти `start:infra` |
| `uv run poe dev:web` | веб-клієнт на машині з гарячим перезавантаженням |
| `uv run poe logs` | логи всіх сервісів; `uv run poe logs api` — одного |
| `uv run poe ps` | стан кожного сервісу |
| `uv run poe clean` | зупинити стек і видалити бази (питає підтвердження) |
| `uv run poe tools` | Portainer: контейнери, їхні логи й стан |
| `uv run poe db:migrate` | застосувати міграції й базове наповнення |
| `uv run poe db:seed:demo` | завантажити великий демонстраційний набір даних |

## Два режими стека

| | `uv run poe start` (розробка) | `uv run poe prod:start` (як на сервері) |
|---|---|---|
| Файли compose | `compose.yaml` + `compose.override.yaml` | лише `compose.yaml` |
| API | код монтується з `backend/`, перезапуск при збереженні | зібраний образ, без вихідного коду |
| Веб-клієнт | production-збірка | production-збірка |
| Середовище застосунку | `development` | `production` |

`compose.yaml` описує систему так, як вона працює на сервері.
`compose.override.yaml` додає поверх неї режим розробки, і `docker compose`
підхоплює його сам, коли файл лежить поруч.

Збірка й запуск production-стека — окремі кроки: `build` збирає образи один
раз, `prod:start` запускає вже зібрані й добирає лише відсутні.

Веб-клієнт в обох режимах зібраний — так стек займає сотні мегабайт пам'яті, а
не гігабайти. Щоб правити клієнт із гарячим перезавантаженням, запусти його на
машині: `uv run poe dev:web` (http://localhost:3100). Він ходить до API через
`http://localhost:8080`.

Production-стек — навчальний стенд, тому базове наповнення з обліковими
записами нижче працює й у ньому. Дозволяє це `SEED_ALLOW_PRODUCTION=true` у
`.env`; без цього рядка наповнення в production відмовляється запускатися.

## Облікові записи

Пароль для всіх трьох — значення `SEED_USER_PASSWORD` з `.env`; `uv run poe start`
друкує його наприкінці.

| Пошта | Роль |
|---|---|
| `admin@crm-training.example` | повний доступ |
| `manager@crm-training.example` | робота з даними |
| `viewer@crm-training.example` | лише читання |

## Адреси

| Адреса | Що це |
|---|---|
| http://localhost:8080 | застосунок — єдина потрібна адреса |
| http://localhost:8080/docs | Swagger UI: контракт API |
| http://localhost:8080/health/ready | стан застосунку та його залежностей |
| http://localhost:9000 | Portainer, після `uv run poe tools`: логін `admin`, пароль у `.portainer-password` |

Порти окремих сервісів теж відкриті — щоб підключитися клієнтом БД або
звернутися до API повз проксі. Сховища слухають лише `127.0.0.1`.

| Змінна в `.env` | Типово | Сервіс |
|---|---|---|
| `HTTP_PORT` | 8080 | застосунок через nginx |
| `API_PORT` | 3000 | API напряму |
| `WEB_PORT` | 3100 | веб-клієнт напряму |
| `POSTGRES_PORT` | 5432 | PostgreSQL |
| `REDIS_PORT` | 6379 | Redis |
| `MONGO_PORT` | 27017 | MongoDB |
| `PORTAINER_PORT` | 9000 | Portainer |

## Склад системи

| Сервіс | Роль |
|---|---|
| `nginx` | єдиний вхід: віддає клієнта, проксує `/api`, `/docs`, WebSocket |
| `web` | веб-клієнт |
| `api` | HTTP API і канал реального часу |
| `migrate` | застосовує міграції та наповнює базу, після чого завершується |
| `postgres` | основне сховище: користувачі, контакти, угоди, товари, замовлення |
| `redis` | кеш і облік частоти запитів |
| `mongo` | журнал доменних подій |
| `portainer` | керування контейнерами й перегляд логів; лише з `uv run poe tools` |

Схема бази накатується автоматично: `migrate` відпрацьовує до старту `api`, а
`api` не запускається, поки той не завершиться успішно. Повторний запуск нічого
не ламає — застосовані міграції пропускаються, а наповнення лише оновлює наявні
записи.

## Структура

```
compose.yaml            система так, як вона працює на сервері
compose.override.yaml   режим розробки поверх неї
.env.example            оточення стека: порти, паролі, секрети
pyproject.toml          команди стека
scripts/                реалізація команд і bash-дублери
etc/nginx/              конфігурація проксі
backend/                HTTP API — див. backend/README.md
frontend/               веб-клієнт — див. frontend/README.md
```

## Файли `.env` — який для чого

| Файл | Коли читається |
|---|---|
| `.env` | стек у Docker: усе його оточення |
| `backend/.env` | API на машині: `uv run poe dev`, тести, міграції |
| `frontend/.env.local` | веб-клієнт на машині: `uv run poe dev:web` |

`setup` створює всі три з шаблонів `*.env.example` з однаковими паролями баз і
однаковими секретами, тож API на машині й API в контейнері працюють з тією самою
базою. Docker бере **тільки** кореневий `.env` і не роздає його контейнерам
цілком: кожен сервіс отримує рівно перелічене в `compose.yaml`.

## Без обгорток

Команди вище — тонкий шар над Docker Compose. Те саме bash-скриптами (у Windows —
з Git Bash):

```bash
./scripts/start.sh        # режим розробки
./scripts/stop.sh
./scripts/build.sh        # production-образи
./scripts/prod-start.sh
./scripts/prod-stop.sh
./scripts/test.sh
```

І напряму:

```bash
docker compose up -d --build --wait                 # розробка: override підхоплюється сам
docker compose -f compose.yaml up -d --build --wait # як на сервері
docker compose logs -f api
docker compose down
```

Без `setup` достатньо скопіювати `.env.example` у `.env`: шаблон містить робочі
локальні значення.

## Якщо не запускається

**Порт зайнятий.** `uv run poe setup` показує зайняті порти заздалегідь; під час
запуску це помилка `port is already allocated`. Постав інше значення в `.env`
(`HTTP_PORT`, `POSTGRES_PORT` тощо) і запусти знову. На Windows порт може бути
зарезервований системою без жодної програми на ньому — це видно з
`netsh interface ipv4 show excludedportrange protocol=tcp`.

**Змінив `.env`, а нічого не змінилося.** Значення потрапляють у контейнер при
його створенні. Потрібно `uv run poe stop`, потім `uv run poe start`; самого `restart` замало.

**Додав залежність, а її не видно.** У режимі розробки віртуальне оточення API
живе в окремому томі, який переживає звичайний перезапуск. Після зміни
`backend/pyproject.toml` зупини стек і видали том — бази при цьому не чіпаються:

```bash
uv run poe stop
docker volume rm practice-crm-python_api_venv
uv run poe start
```

**Змінив файл, а нічого не сталося.** Зміни відстежуються опитуванням раз на
пів секунди, тож дай пару секунд. Якщо не допомогло — `uv run poe logs api`:
там видно, чи застосунок узагалі перезапустився. Зміни веб-клієнта в контейнері
не підхоплюються взагалі — для них `uv run poe dev:web`.

**Логи виглядають як суцільний JSON.** Так і має бути: у контейнері немає
інструмента розфарбовування, він потрібен лише в розробці. Читабельні логи —
у запуску на машині через `uv run poe dev`.

**Що зі стеком насправді.** `uv run poe ps` показує стан кожного сервісу, а
`/health/ready` — чи бачить API свої залежності. Якщо якесь сховище лежить,
воно буде названо там поіменно.

**MongoDB падає одразу після старту на старому комп'ютері.** MongoDB 5 і новіші
потребують процесора з підтримкою AVX. На машинах без неї контейнер `mongo`
завершується без зрозумілого повідомлення.
